# Femto Bolt Docker 배포

`compose.live.yml`은 실센서 웹 단말입니다. 실제 Femto Bolt의 RGB·깊이·IR 미리보기와 함께 로그인 없는 계정 관리,
명시적 동의, 중앙 서버 안내에 따른 얼굴 등록·인증을 제공합니다. 비밀번호 로그인은 콘솔 모드를 끈 구성에서 지원합니다.
여러 사람을 등록한 뒤에는 화면을 열어 두면 얼굴별 박스와 표시 이름을 자동으로 보여주는 라이브 인식을 사용합니다.
원본 프레임은 메모리에서만 처리하고 시뮬레이터로 대체하지 않습니다. GPU 추론·검색 서버와 점수 관측 경로가
준비되었습니다. 현재 내부망 파일럿은 사용자의 명시적 요청에 따라 **PAD 비활성 모드**로 진행합니다.
실제 계정·얼굴 신원을 확인하며 생체·위조 여부는 판정하지 않습니다. PAD 검증 완료를 의미하지 않습니다.

## 실행과 접속

```bash
cd /home/junghoonseo/Codes/PaceAuth
# 기존 배포의 키·모델·DB가 준비된 상태에서 backend와 외부 네트워크를 먼저 시작
docker compose up -d db db-standby1 db-standby2 kms api-1 api-2 gateway
docker compose -f compose.live.yml up -d --build
docker compose -f compose.live.yml ps
curl -fsS http://127.0.0.1:8080/healthz
curl -sS http://127.0.0.1:8080/api/status
```

`.env`의 `FA_LIVE_BIND_IP=0.0.0.0`, `FA_LIVE_PORT=8080`으로 같은 내부망에 공개합니다.
현재 PC 주소는 `192.168.2.218`이므로 `http://192.168.2.218:8080`으로 접속합니다.
주소가 바뀌면 `hostname -I`로 확인합니다. 이 PC에서만 사용할 때는 `FA_LIVE_BIND_IP=127.0.0.1`로 바꾸고
`docker compose -f compose.live.yml up -d`를 실행합니다. 웹은 별도 파일럿 계정으로 로그인하며,
현재 HTTP 내부망 배포에는 다른 서비스에서 쓰는 비밀번호를 사용하지 않습니다.

이 compose는 기존 인증 스택이 생성한 **외부 네트워크 `faceauth_edge`**에 연결하여 `https://gateway:8443`으로
통신합니다. 빈 호스트에서 웹 compose만 실행하면 네트워크·키·backend가 자동으로 준비되지 않습니다.
새 설치는 README의 키·모델·DB 초기화 절차를 먼저 완료합니다.

`-f compose.live.yml`을 꼭 지정합니다. `.env`의 기본 `COMPOSE_FILE`은 기존 GPU 인증 클러스터를 가리킵니다.
컨테이너는 `restart: unless-stopped`로 설정되어 있어 실행 중 재부팅하면 Docker 시작 후 다시 올라옵니다.
직접 `stop`한 경우에는 위의 `up -d` 명령으로 다시 시작합니다.

| 경로 | 의미 |
|---|---|
| `/healthz` | 웹 프로세스 정상 여부. 센서가 없어도 200 |
| `/readyz` | 최근 3초 이내 RGB·깊이·IR 수신 시 200, 아니면 503. 응답의 `authentication_ready`는 별도 판정 |
| `/api/status` | 센서 상태·FPS·중앙 깊이, 로그인 상태, `auth.ready`·`auth.capture_ready`와 차단 사유 |
| `/api/preview/rgb.jpg` | 현재 컬러 영상, 프레임이 없거나 오래되면 503 |
| `/api/preview/depth.jpg` | 깊이 표시용 색상 영상. 검은색은 무효 깊이 |
| `/api/preview/ir.jpg` | 적외선 표시 영상 |
| `/api/live/faces` | 최신 다중 얼굴 박스·이름·상태·인식 FPS. 인증 승인과 별개인 데모 결과 |
| `/api/auth/signup`, `/api/auth/login`, `/api/auth/logout` | 별도 테스트 계정 가입·비밀번호 로그인·로그아웃 |
| `/api/auth/profile` | 로그인한 자신의 표시 이름 변경. 얼굴 재등록 없이 반영 |
| `/api/auth/enroll`, `/api/auth/authenticate` | 동의 후 실제 등록·인증 시작. `auth.ready`가 필요 |
| `/api/auth/observe` | 동의 후 PAD 관측 표본 수집. `observation_mode`로 진단/인증/등록 선택기를 지정하며 승인 없음 |
| `/api/auth/operation`, `/api/auth/cancel` | 현재 로그인 세션 소유 작업의 상태 확인·촬영 취소 |

현재 `.env`에는 `FA_PILOT_DISABLE_PAD=1`을 지정하고 API·엔진에 공통 적용합니다.
기본값은 `0`이며, 정확히 `1`로 설정한 파일럿만 등록·인증의 PAD 검증 gate와 프레임 PAD 판정을
사용하지 않습니다. 준비 상태·등록·인증 결과·서명된 승인 토큰·감사 기록에는
`pad_enabled=false`, `pad_mode=disabled_pilot`가 포함됩니다. `pad_validation`은 기존 모델의 실제
미검증 상태를 계속 반환합니다. API·엔진의 설정이 다르면 `pad_mode_mismatch`로 요청을 거절합니다.
설정을 변경한 뒤 `python3 scripts/start_gpu_backend.py`로 API와 GPU 서비스를 적용·점검합니다.

중앙 깊이는 화면 중앙 영역의 유효값 중앙값이며 얼굴 거리를 검출한 값이 아닙니다.
연결이 끊기면 마지막 영상을 계속 보여주지 않습니다.

사용자를 마주 보는 카메라이므로 컬러·깊이·IR 미리보기는 기본적으로 거울처럼 좌우 반전합니다.
등록 안내의 왼쪽·오른쪽은 촬영하는 사람 기준이며, 글자와 방향 안내는 반전하지 않습니다.
화면 표시 단계에서만 반전하므로 센서 보정, 서버로 보내는 RGB-D-IR 좌표, 기존 얼굴 특징은 유지됩니다.
녹화 재생 키오스크와 영상의 센서 패널도 같은 거울 보기 기준을 사용합니다.

화면은 **센서 수신 FPS**와 **화면 표시 FPS**를 따로 보여줍니다. 미리보기 요청에
`?after=<직전 X-Frame-Sequence>&wait_ms=1000`을 붙이면 새 프레임까지 최대 1초 기다립니다.
새 JPEG에는 `X-Frame-Sequence`와 `X-Frame-Age-Ms`가 포함되고, 변경이 없으면 204,
센서가 끊기거나 프레임이 오래되면 503입니다. 브라우저는 한 요청만 유지하고 새 프레임을 그린 뒤
다음 요청을 시작합니다. 느린 접속자는 최신 프레임으로 건너뛰며 영상 대기열을 쌓지 않습니다.

## 웹 계정·동의와 준비 상태

현재 내부망 배포는 `FA_LIVE_OPEN_CONSOLE=1`로 **로그인 없는 관리자·데모 화면**을 제공합니다.
페이지에 접속하면 계정을 관리할 수 있고, 라이브 화면에서 촬영 대상 계정을 선택합니다. 사람을 추가할 때
비밀번호를 입력할 필요가 없습니다. 촬영 대상 본인이 동의문에 명시적으로 동의해야 촬영을 시작합니다.
브라우저별 작업 세션은 자동으로 준비하며, 다른 브라우저의 촬영 작업을 가져오거나 취소하지 않습니다.
콘솔 접근은 얼굴 인증 성공을 뜻하지 않으며, 얼굴 일치는 실제 선택한 계정의 등록 정보와 비교합니다.
등록은 중앙 엔진의 품질·고개 방향 안내로 9방향의 18프레임을 선택하고, 인증은 정면 품질을 통과한
3프레임을 선택합니다. 서버 challenge를 받은 뒤 새 프레임을 모으며 실제 센서 타임스탬프를 전송합니다.
등록 촬영은 화면에 한 명만 있어야 합니다. 인증 촬영에서 여러 얼굴이 검출되면 화면에 보이는 박스 면적이
가장 큰 얼굴을 선택합니다. 그 얼굴이 품질 기준을 통과하지 못해도 다른 작은 얼굴로 바꾸지 않습니다.
선택된 사람의 얼굴 특징이 3프레임 사이에 바뀌면 인증은 재시도로 끝나며, 여러 사람의 특징을 평균 내서
승인하지 않습니다. 가장 큰 얼굴은 가까운 사람을 고르는 기준이며 깊이 순으로 사람을 정렬하는 것은 아닙니다.
최종 결과는 기존 mTLS API의 센서 품질·신원·정책 판정으로 결정합니다. PAD 사용 모드에서는 PAD 판정도
추가로 적용합니다. 브라우저에는 개인키·계정 주장·임베딩·
승인 토큰을 전달하지 않으며, 웹 단말은 승인 서명과 현재 계정·장치·행위·세션의 일치를 확인합니다.

| 준비 상태 | 허용 범위 |
|---|---|
| 센서 streaming | RGB·깊이·IR 미리보기. backend의 GPU 상태와 별개 |
| `auth.capture_ready=true` | 등록된 장치·보정과 중앙 추론 경로가 준비됨 |
| `auth.ready=true` | 현재 PAD 사용 설정을 반영한 중앙 준비 조건을 충족해 등록·인증 시도 가능. 각 시도의 판정은 다시 수행 |

현재 사용 흐름은 계정 추가·선택 → 촬영 동의 → 9방향 얼굴 등록 → 정면 얼굴 일치 확인입니다.
PAD 수집·학습·검증은 현재 파일럿의 진행 조건이 아닙니다.

`FA_LIVE_OPEN_CONSOLE`을 끄면 기존 ID·비밀번호 로그인 모드를 사용합니다. 기존 비밀번호는 salt를 사용한
scrypt 해시로, 로그인 세션은 토큰 해시로 보관하며 계정 관리에는 관리자 로그인이 필요합니다.

## 여러 사람을 등록하는 라이브 데모

1. 페이지를 열고 상단 **계정 관리 → 계정 추가**에서 이름을 입력합니다. 아이디는 필요하면 직접 지정합니다.
2. 목록에서 등록할 사람을 선택하고 **얼굴 등록**을 누릅니다. 카메라 앞에는 해당 사람 한 명만 둡니다.
3. 등록 대상 이름을 확인하고 본인의 생체정보 처리 동의를 받아 9방향 촬영을 완료합니다. 등록 사진도 보관하려면
   별도의 **등록 사진 저장 동의**를 선택합니다. 다음 사람도 같은 방법으로 등록할 수 있습니다.
4. 등록이 끝나면 화면을 열어 둡니다. 여러 사람이 카메라에 들어오면 자동으로 얼굴별 박스와 이름이 표시됩니다.
5. 얼굴 일치를 확인하려면 라이브 화면에서 대상 계정을 선택·동의하고 **인증 시작**을 누릅니다.

대상 계정을 바꾸면 촬영 동의를 다시 받습니다. 여러 사람이 보이면 가장 크게 보이는 얼굴로 선택한 계정과 일치하는지 확인합니다.

### 계정 관리와 등록 사진

계정 관리 목록에서 이름 수정, 활성/비활성 전환, 사진 삭제, 얼굴·사진 다시 등록, 계정 삭제를 할 수 있습니다.
열린 콘솔에서는 계정의 관리자 등급과 관계없이 관리할 수 있으며, 관리자를 나타내는 숨은 사용자 계정을 만들지 않습니다.
기존 로그인 모드로 돌아가면 현재 로그인한 관리자와 마지막 활성 관리자는 비활성화하거나 삭제할 수 없습니다.
기존 테스트 계정의 관리자 설정과 비밀번호는 콘솔 모드 전환으로 변경하지 않습니다.

비활성화하면 기존 로그인 세션을 폐기하고 라이브 이름 표시·얼굴 인증·신규 얼굴 등록을 차단합니다.
얼굴 특징과 사진은 유지하므로 다시 활성화하면 사용할 수 있습니다. 중앙 API도 최종 판정 때 상태를 확인하므로
검색 복제본에 이전 결과가 남아 있어도 비활성 계정이 승인되지 않습니다.

계정 삭제는 확인창에서 선택한 계정에만 적용하며 로그인 정보·사진을 삭제하고 모든 과거 얼굴 특징과 KMS 키를 폐기합니다.
검색 복제본 반영까지 확인하지 못하면 성공으로 표시하지 않고 계정을 비활성 상태로 남깁니다. 같은 삭제를 재시도할 수 있습니다.
사진만 삭제하면 얼굴 등록은 유지됩니다. 다시 등록하면 기존 얼굴과 사진을 새 촬영으로 교체합니다.

등록 사진은 성공한 등록의 정면 프레임에서 만들며 별도 동의 없이 저장하지 않습니다. JPEG 메타데이터를 제거하고
최대 320px로 축소한 뒤 AES-GCM으로 `live-state`의 계정 DB에 암호화해 저장합니다. 별도 키 파일과 동의 시각·버전도
같은 영속 볼륨에 보관합니다. 사진은 계정 관리 화면에서 조회하며 브라우저 캐시를 금지합니다.
기존 등록에는 사진이 없으므로 다시 등록해야 사진이 생깁니다. 라이브 연속 영상·깊이·IR 영상은 저장하지 않습니다.

신규 계정 관리 배포 시 `deploy/db/migrations/002_account_management.sql`을 DB 소유자 `faceauth_api`로 적용한 뒤
API·검색 복제본을 재시작해야 합니다. 웹 단말에 마운트하는 `admin_token`은 서버 내부 mTLS 호출에서만 사용하며
브라우저에는 전달하지 않습니다. 기존 계정의 관리자 지정은 공개 가입과 분리한 `Accounts.bootstrap_admin()`으로 수행합니다.

기존 계정에는 처음에 계정 ID가 표시 이름으로 설정됩니다. **계정 관리**에서 이름을
수정할 수 있으며, 이름 변경에 얼굴 재등록은 필요하지 않습니다. 새 계정도 이름을 비우면 계정 ID를 사용합니다.
표시 이름은 해당 웹 단말의 계정 DB에 보관하며, 계정 ID·암호화된 얼굴 특징은 바뀌지 않습니다.

메인 화면에는 카메라와 계정·동의·얼굴 확인 흐름을 표시합니다. 얼굴 등록을 시작하면 거울 영상이 큰 원 안에
표시되고, 고개를 움직여 실제 촬영된 방향부터 바깥 눈금이 파란색으로 채워집니다. 정면 촬영은 별도로 표시하며
전체 진행률에는 정면을 포함한 9방향을 모두 반영합니다. 등록은 `circle` 가이드를 사용하고 품질 문제나 부족한
방향이 있으면 구체적인 안내를 보여줍니다. 눈금이 채워져도 서버의 등록 판정이 끝나기 전에는 성공으로 표시하지 않습니다.

## 기존 실제 사용·PAD 진단 기록

2026-10-14 실제 참여자 1명이 이 웹 흐름으로 등록·얼굴 일치 확인에 성공했습니다. 서버 감사 기록에서도
9방향 등록 활성화와 인증 승인을 확인했고, 암호화된 얼굴 특징 4개가 저장되었습니다. 두 결과 모두
`pad_enabled=false`, `pad_mode=disabled_pilot`입니다. 여러 사용자·조건의 인식 정확도를 검증한 것은
아닙니다([실제 사용 검증 기록](../reports/deployment/femto_bolt_pilot_success_20261014.json)).

아래 PAD 관측 기능은 별도의 진단용이며 현재 사용자 등록·인증 흐름에서는 사용하지 않습니다.
`observe` 경로 자체는 비활성 파일럿에서도 PAD 점수를 측정할 수 있습니다. 대상 코드, 생체/사진/화면/가면 유형,
보정/시험 split과 공격 도구 코드를 입력하고
동의한 뒤 실행합니다. 요청의 `observation_mode`는 다음 세 가지이며 기본값은 `diagnostic`입니다.

| 관측 모드 | 실제 프레임 선택 | 평가에서의 용도 |
|---|---|---|
| `diagnostic` | 고정 간격의 정면 5프레임, 품질 불합격 포함 | 센서 분포 진단. 운영 인증·등록의 합격 표본에서 제외 |
| `auth` | 실제 인증과 같은 정면·품질 선택기로 3프레임 | 인증 선택 경로의 PAD 평가 자료 |
| `enroll` | 실제 등록과 같은 Guide로 9방향별 2프레임, 총18프레임 | 등록 선택 경로의 PAD 평가 자료 |

세 모드 모두 `auth.capture_ready`로 실행하는 **점수 관측**입니다. 실제 선택기를 사용하더라도
얼굴 템플릿 생성·등록 완료·인증 승인을 수행하지 않습니다. 원본 영상·깊이·IR·랜드마크·임베딩은
저장하지 않고 승인 토큰도 발급하지 않습니다. 처음 수집한 생체 진단 32시도·160프레임은 모두 PAD를
통과하지 못했습니다. 600–700mm 구간도 품질 10/10프레임, 물리 검사 9/10프레임을 통과했지만
PAD는 0/10프레임이었습니다. 이 진단은 한 참여자의 보정 자료이며 검증 완료 자료가 아닙니다
([측정 기록](../reports/deployment/femto_bolt_first_live_diagnostics_20261014.json)).
표본 계획·평가 명령·서명된 검증 gate는 [Femto PAD 검증 문서](FEMTO_PAD_VALIDATION.md)에 있습니다.

쓰기 가능한 영속 영역은 `live-state` 볼륨의 `/var/lib/paceauth`입니다.
`accounts.sqlite3`에 테스트 계정·표시 이름·세션을, `pad-observations.jsonl`에 동의한 관측의 점수와 실험 코드를
보관합니다. 컨테이너 재생성 후에도 남습니다. 원본은 최신 미리보기 1세트와 진행 중 작업에 필요한
제한된 프레임만 메모리에 유지합니다. 점수 기록도 실험 참여 자료이므로 보관·삭제 대상으로 관리합니다.

웹 단말에는 CA 공개 인증서, `dev-001`의 mTLS 인증서·개인키 및 촬영 서명키,
파일럿 계정 주장용 `account.key`, 승인 검증용 `approval.pub`, 계정 관리 호출용 `admin_token`을
읽기 전용으로 마운트합니다. 전체 `secrets/` 디렉터리나 DB·KMS 키는 전달하지 않습니다.
관리 토큰은 콘솔 모드 또는 관리자 세션을 확인한 서버 내부에서만 사용합니다. 모델 디렉터리도 읽기 전용입니다.

## 센서 진단

카메라는 한 프로세스만 사용합니다. 프로브 전에 웹 단말을 잠깐 중지합니다.

```bash
docker compose -f compose.live.yml stop terminal
docker compose -f compose.live.yml run --rm --no-deps terminal python /app/scripts/probe_orbbec.py --info
docker compose -f compose.live.yml run --rm --no-deps terminal python /app/scripts/probe_orbbec.py --fps 30 --frames 300
docker compose -f compose.live.yml up -d
docker compose -f compose.live.yml logs --tail 50 terminal
```

`--frames`는 실제 세 모달리티 수신에 성공해야 종료 코드 0을 반환합니다. `--info`는 장치 열거용이며
스트리밍 성공을 의미하지 않습니다. 마지막 `ready` 행의 `observed_fps`는 첫 프레임부터 마지막 프레임까지
실제 수신 간격으로 계산한 속도입니다. 설정값 `fps`와 구분해서 확인합니다. 원본 영상은 저장하지 않습니다.

SDK는 `pyorbbecsdk2==2.1.2`이고 Python import 이름은 `pyorbbecsdk`입니다. SDK가 함께 요구하는 GUI OpenCV 대신
명시적으로 headless OpenCV를 설치합니다. Femto 깊이 엔진에는 `libEGL.so.1`도 필요하므로 이미지에 EGL/Mesa를 포함합니다.
USB 장치는 `/dev/bus/usb`와 USB 문자 장치 major 189만 허용합니다. 전체 `privileged` 모드는 사용하지 않습니다.
SDK의 초기 파일 로그는 쓰기 가능한 `/tmp`에서 생성되고 이후 비활성화됩니다.

깊이 엔진의 EGL 연산에는 AMD 내장 GPU를 사용합니다. `compose.live.yml`은 렌더 노드 하나만 컨테이너에
전달하며, `.env`의 `FA_DRM_RENDER_NODE`는 이 PC의 `/dev/dri/by-path/pci-0000:0b:00.0-render`를 가리킵니다.
다른 PC에서는 사용 가능한 렌더 노드로 변경합니다. 이 장치를 전달하지 않으면 현재 이미지의 Mesa는
llvmpipe 소프트웨어 렌더러를 사용합니다. 실제 비교에서 GPU 연결은 깊이 엔진의 CPU 부담을 크게 줄였지만
480 Mbps USB 링크의 전송 제한까지 해결하지는 못했습니다. NVIDIA GPU의 얼굴 모델 추론과는 별개입니다.

2026-10-14 USB 재연결 후 OS/SDK에서 **5,000 Mbps / USB 3.1**을 확인했습니다.
현재 `.env`는 `FA_ORBBEC_FPS=30`이며 컬러 1280×720 MJPG, 깊이·IR 640×576 Y16 해상도를 유지합니다.
AMD 내장 GPU를 사용한 동기 캡처 시험 결과는 다음과 같습니다.

| 설정 | 시험 시간 | 수신 프레임 | 실측 FPS | 타임아웃 | 최대 모달리티 시간 차이 |
|---|---:|---:|---:|---:|---:|
| 15 FPS | 40초 | 589 | 14.95 | 0 | 2ms |
| 30 FPS | 40초 | 1,194 | 30.12 | 0 | 2ms |

최종 배포에서 RGB·깊이·IR을 각각 요청하는 3개 접속을 120초 동시에 유지해 각 3,614프레임,
약 30.1 FPS, HTTP 오류 0회를 확인했습니다. 같은 시점의 실제 Chrome은 5초간 150프레임을
표시했고 화면 표시값은 30.0 FPS였습니다. 내부망 `192.168.2.218:8080` 접속도 확인했습니다.
수치 기록은 [USB 3 센서 시험](../reports/deployment/femto_bolt_usb3_20261014.json),
[웹 부하 시험](../reports/deployment/femto_bolt_web_20261014.json),
[재연결 전 비교 시험](../reports/deployment/femto_bolt_usb2_20261014.json)에 있습니다.

재연결 전 480 Mbps 상태에서는 5 FPS만 안정적이었습니다. RGB 단독은 30 FPS였지만 깊이·IR은 약
6.7 FPS에서 제한됐고, 해상도를 320×288로 줄이거나 GPU를 연결해도 동일했습니다.
[해당 SDK의 원시 프레임 구성](https://github.com/orbbec/OrbbecSDK_v2/blob/2f6561c28255d805b34aa00a690199ce40e96c81/src/device/femtobolt/rawphase/RawPhaseStreamer.cpp#L69-L72)은
두 NFOV 모드 모두 7680×434×16비트이므로 15 FPS에 약 800 Mbps가 필요합니다.
초기의 `DeviceComponentPtr is nullptr`와 `raw phase streamer not found` 오류는 EGL/Mesa 설치로,
CPU 깊이 연산은 GPU 렌더 노드 전달로, USB 대역폭 제한은 실제 5 Gbps 링크 연결로 각각 해결했습니다.

브라우저의 기존 500ms 폴링은 약 2 FPS 상한이 있어 새 프레임 대기 방식으로 교체했습니다.
깊이 정합의 중복 정렬도 동일 결과를 내는 최소값 연산으로 바꾸어 합성 데이터의 처리 시간을 약 55→28ms로
줄였습니다. 실센서의 30 FPS 시험에서 정합 평균은 7.34ms였습니다. 원본 데이터 밀도가 달라 두 수치를
직접 비교하지 않습니다. 미리보기는 최신 1세트만 보관하고 촬영 영상은 파일로 저장하지 않습니다.
Python 3.11/OpenCV 4 미리보기 이미지와 Python 3.12/OpenCV 5 CLI 이미지 양쪽에서 실제 장치 수신을 확인했습니다.
OpenCV 5에서 변경된 보정 함수 호출도 호환 처리했습니다.

`lsusb -t`의 속도는 포트의 표시 규격이 아니라 현재 협상된 링크입니다. USB 3 포트라도 480M이면 OS 관점에서는
USB 2 속도입니다. 전원, 케이블, 중간 허브, 컨테이너 라이브러리를 함께 진단해야 합니다.

정합은 장치 내장 카메라 보정값으로 깊이와 IR을 같은 컬러 좌표계에 투영합니다. 가까운 깊이값과 해당 IR 샘플을
함께 선택하고 빈 픽셀은 0으로 남깁니다. 타임스탬프 차이가 15ms를 넘거나 순서가 역전되면 프레임을 거절합니다.
장치·펌웨어·보정·전처리 설정에서 `femto-bolt-v1-…` 보정 ID를 생성합니다.

## GPU와 인증 서버 준비

호스트 사전 점검은 Python 표준 라이브러리만 사용하며 설정을 바꾸지 않습니다.

```bash
python3 scripts/deployment_preflight.py
python3 scripts/deployment_preflight.py --verify-hashes --json
```

2026-10-14 재부팅 후 **`7.0.0-38-generic`**에서 RTX 4060과 NVIDIA 드라이버 `580.178.04`가
구동되었습니다. Docker 내부의 CUDA·FAISS 실제 연산을 통과했고, `engine-1`/`engine-2`와
`search-1`/`search-2`가 모두 healthy입니다. 웹은 `auth.capture_ready=true`를 반환합니다.
이전 커널 `7.0.0-28-generic`에 NVIDIA 모듈이 없었던 문제는 재부팅으로 해결했습니다.
센서의 AMD 내장 GPU 처리와 30 FPS 미리보기도 함께 동작합니다. 이후 시작·복구 점검 명령은 다음과 같습니다.

[GPU 시작·워밍업 기록](../reports/deployment/femto_bolt_gpu_20261014.json)은 실제 CUDA·FAISS 실행과
두 추론 복제본의 검출·고개 방향·얼굴 특징·PAD 합성 입력 워밍업을 담습니다. 이 기록은 PAD를 끄기 전
구성의 시험이며 대규모 등록 갤러리 부하는 포함하지 않습니다. 당시 모델 binding 및 PAD 차단 사유는
[PAD 준비 상태 기록](../reports/deployment/femto_bolt_pad_readiness_20261014.json)에서 확인합니다.

```bash
uname -r
nvidia-smi
python3 scripts/start_gpu_backend.py --check-only --json
python3 scripts/start_gpu_backend.py
```

시작 스크립트는 호스트와 Docker의 실제 CUDA·FAISS 연산을 먼저 확인하고 기존 DB·KMS·API·gateway,
추론·검색 복제본을 시작합니다. GPU 서비스는 순서대로 준비 상태를 확인합니다. 드라이버 설치·재부팅·
모델 교체·볼륨 초기화를 대신하지 않습니다. 성공 결과의 범위도 GPU와 서비스 준비 상태이며 PAD 검증
또는 실제 얼굴 인증 성공을 뜻하지 않습니다.

기존 클러스터는 `.env`의 `FA_GPU_DEVICE_ID=0`을 사용합니다. 서버 이미지 빌드는 GPU 드라이버와 별개입니다.

```bash
docker build -f docker/Dockerfile -t faceauth:dev .
```

기존 원본 가중치를 `/fdisk2/Codes/jhseo/faceauth/data/models`에서 찾았고, 이 체크아웃에 필요한 SCRFD,
6DRepNet360, FaRL, AdaFace, kprpe, PAD v2 파일을 `MODEL.json`의 SHA-256과 대조해 복원했습니다.
현재 `.env`의 인증 모델과 임계값은 AdaFace 설정을 유지합니다. 모델 파일은 git에 추가하지 않습니다.

이 배포용 새 키를 생성하고 복원된 파일만 포함하는 레지스트리를 다시 서명했습니다. 키와 모델을 다시 준비할
때는 README의 인증 서버 절차를 따릅니다. 기존 배포의 개인키는 복사하지 않았습니다.
`scripts/build_registry.py --skip-invalid`는 사용 가능한 모델만 등록하고, 처음 활성화할 때는 이름별 가장 낮은
버전을 선택합니다. 이 배포는 터미널과 일치하도록 `scrfd_34g@2`를 활성화하고 감사 로그를 남겼습니다.

DB 기본 노드와 복제 노드 2개, KMS, API 2개, mTLS gateway는 실행 중이며 DB 복제도 확인했습니다.
실제 센서의 30 FPS 보정 ID `femto-bolt-v1-50beeef1ae82fb27`과 `dev-001` 장치 인증서를 API에 등록했습니다.
FPS나 스트림 프로파일을 변경하면 보정 ID도 달라지므로 장치 등록을 갱신합니다. PAD 사용 모드에서는
해당 설정의 PAD 검증도 다시 확인합니다. 운영자 CLI의 `--register`도 장치 갱신 경로입니다. 추론·검색 서비스는 위 시작 스크립트로
확인합니다. 기존 데이터와 키를 지우거나 `down -v`를 실행할 필요가 없습니다.

```bash
# 서비스 시작 결과와 웹에 노출되는 차단 사유 확인
docker compose ps
docker compose logs --tail 50 engine-1 search-1
curl -sS http://127.0.0.1:8080/api/status
```

기존 PAD 모델의 보정은 `gemini336-sim-v1`이며 실제 Femto 검증 자료가 없어
`pad_calibration_mismatch`, `pad_real_sensor_validation_missing`이 남습니다.
PAD 사용 모드에서는 중앙 API와 엔진이 이 상태의 등록·인증을 차단합니다. 현재 PAD 비활성 파일럿은
이 검증과 프레임별 PAD 판정을 사용하지 않고 기존 센서 품질·서명·계정·신원 검사를 수행합니다.

## 실제 센서 CLI 시험

`scripts/terminal_demo.py --source orbbec`는 실센서 프레임으로 기존 등록·인증 경로를 호출합니다.
서버 challenge를 받은 뒤 매 단계에서 센서를 새로 시작하고, 실제 프레임 타임스탬프와 보정 ID를 전송합니다.
이 CLI는 계정 확인·추가 인증을 `secrets/account.key`로 모사하는 운영자용 시험 도구입니다.
실서비스의 사용자 계정 로그인이나 동의 UI를 대신하지 않습니다.
CLI의 `--fps` 기본값은 **30**으로 현재 웹 설정과 같습니다. 아래 예시는 설정을 분명히 하기 위해
`--fps 30`을 명시합니다. 웹 계정 로그인·동의 흐름과 CLI의 계정 주장 모사는 구분합니다.

```bash
docker compose -f docker-compose.yml -f deploy/compose.terminal.yml --profile hardware-tools build terminal
# 카메라는 한 프로세스만 사용하므로 웹 미리보기를 잠깐 중지합니다.
docker compose -f compose.live.yml stop terminal
docker compose -f docker-compose.yml -f deploy/compose.terminal.yml --profile hardware-tools run --rm terminal \
  python /app/scripts/terminal_demo.py --source orbbec --fps 30 --models /app/data/models \
  --device dev-001 --register --account pilot-001
docker compose -f compose.live.yml up -d
```

등록을 건너뛰고 재인증할 때는 `--skip-enroll`을 추가합니다. 현재 이 CLI의 패킷·리소스 정리·모드 분기 테스트는
통과했지만, 실제 GPU에서 사람을 등록하고 승인받는 통합 시험은 아직 수행하지 않았습니다.

한 명의 실제 웹 등록·인증은 위 기록에서 확인했습니다. 추가 확인 항목은 여러 참여자의 등록·이름 표시,
미등록자 구분, 동시 인식 속도와 가장 큰 얼굴의 실제 인증입니다. PAD 재학습이나 원본 수집을 추가하지 않습니다. PAD를 다시 사용하려면
기존 [PAD 검증 문서](FEMTO_PAD_VALIDATION.md)의 조건을 적용합니다.

센서 미리보기 정상, 웹 healthcheck 정상, 전체 인증 성공은 각각 별도로 확인합니다.
